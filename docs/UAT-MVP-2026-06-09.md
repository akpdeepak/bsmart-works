## Bugs Fixed This Session

### BF-1 · P1 · `WorkItemController.java` — `mapRow` missing `version` field
**Symptom:** Every `PUT /work-items/{id}` returned **409 Conflict** ("This work item was changed by someone else") for any item that had been updated at least once. All status changes, title edits, and field updates in the detail panel silently failed.

**Root cause:** `WorkItemController.mapRow()` (line 224) never read the `version` column from the SQL `ResultSet`. The `private Integer version = 0` field default meant every item the frontend loaded via `GET /work-items` or `GET /work-items/{id}` carried `version: 0`. The JPA `repository.findById()` used inside the `PUT` handler read the real version from the DB (e.g., `1`). `ConcurrencyGuard.requireCurrentVersion(1, 0)` then rejected every write.

**Fix (1 line, `WorkItemController.java:224`):**
```java
w.setVersion(rs.getObject("version") != null ? rs.getInt("version") : 0);
```

**Verified:** `GET /work-items/WRK-CA` now returns `"version": 4`; subsequent `PUT` with that version succeeds and returns `"version": 5`. Status change via detail panel works end-to-end.

### BF-2 · P2 · `App.jsx:717` — `/users` called without required `workspaceId` parameter
**Symptom:** `GET /api/v1/users → 500` on every page load. The Assignee dropdown in the work-item detail panel always showed only "Unassigned" with no users to select.

**Root cause:** `UserController.getAllUsers(@RequestParam String workspaceId)` requires `workspaceId`. The frontend called `api.raw('/users')` without it; Spring's `MissingServletRequestParameterException` became a 500. The `setUsers([])` fallback left the dropdown empty.

**Fix (1 line, `App.jsx:717`):**
```js
// Before
api.raw(`/users`).then(r => r.json()),
// After
api.raw(`/users?workspaceId=${encodeURIComponent(activeWorkspaceId)}`).then(r => r.json()),
```

**Verified:** `GET /api/v1/users?workspaceId=WS-001 → 200` returns `[{id: "USR-DEV1", fullName: "Deepak Pandey"}, {id: "USR-AKP", fullName: "AKP Dev Account"}]`. Assignee dropdown now populated.

### BF-3 · P3 · `index.css` — Tailwind v4 `extend.width` tokens don't auto-generate `w-*` utilities
**Symptom:** `WorkItemDetailPanel` rendered at **1px wide** (invisible). Classes `w-panel`, `w-sidebar`, `w-rail`, `w-subrail` had no CSS rules.

**Root cause:** Tailwind v4 changed how `@config` compat mode handles `theme.extend.width`. In v3, `extend.width: { panel: '360px' }` automatically generated `.w-panel { width: 360px }`. In v4, `@config` loads the v3-compat bridge but **only `--spacing-*` and `--color-*` CSS custom properties auto-generate utilities**. The `--width-*` vars defined via `@theme` do not. Each utility must be declared explicitly via `@utility`.

**Fix (`index.css` — added `@theme` block + `@utility` declarations):**
```css
@theme {
  --width-panel:             360px;
  --width-sidebar:           240px;
  --width-sidebar-collapsed: 48px;
  --width-rail:              72px;
  --width-subrail:           208px;
  --width-reading:           880px;
}

@utility w-panel             { width: var(--width-panel); }
@utility w-sidebar           { width: var(--width-sidebar); }
@utility w-sidebar-collapsed { width: var(--width-sidebar-collapsed); }
@utility w-rail              { width: var(--width-rail); }
@utility w-subrail           { width: var(--width-subrail); }
@utility max-w-reading       { max-width: var(--width-reading); }
```

**Verified:** `WorkItemDetailPanel.offsetWidth = 360`. Panel renders correctly at full 1440px viewport.

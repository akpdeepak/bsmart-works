# Internationalization (i18n) — bSmart Works frontend

> Iteration-20 Cap A: localization across 10 languages (en/hi/es/fr/de/pt/ja/zh/ar/ko),
> RTL-aware. This document is the pattern reference for extending i18n to new surfaces.

## What exists

The frontend ships a small, **dependency-free** i18n runtime (no `react-i18next`/`intl`
library — keeps the bundle lean, RB-10 §1: "build to the code that exists"). It has three parts:

| File | Role |
|------|------|
| `src/lib/locales.js` | The flat string catalogue (`MESSAGES`), the locale list (`LOCALES`), `RTL_LOCALES`, `DEFAULT_LOCALE`, and `translate(locale, key)` with English fallback. |
| `src/lib/i18n.jsx` | `<I18nProvider>` (mounted in `main.jsx`), the `useI18n()` hook exposing `{ locale, setLocale, t, locales }`, and the `<html lang/dir>` side-effect for RTL. |
| `src/components/works/organisms/language-switcher.jsx` | The labelled `<select>` switcher (mounted in the workspace/account view) that calls `setLocale`. |

### How a locale change flows
1. `setLocale(code)` updates React state, writes `localStorage['works.locale']` (instant first
   paint on reload), persists to the server (`PUT /users/me/locale` via `apiClient`), and sets
   `document.documentElement.lang` + `dir` (`rtl` for Arabic).
2. On mount, `I18nProvider` reconciles with the signed-in user's saved `locale` from `/users/me`.
3. Components read strings through `t('some.key')`. A missing key falls back to English, then to
   the key itself — **never a blank string**.

### Dates / numbers
Do **not** hand-format. Use the single locale-aware formatting layer in `src/lib/format.js`
(`absoluteDate`, `smartDate`, `formatNumber`, `formatPercent`, …) — RB-30 §8.

## Translation status (honest)

- **English (`en`)** — the source of truth. Fully populated for every externalized key.
- **The other 9 locales** — navigation/common/work-item strings are translated; the
  **Insights surfaces** (`insights.*`) currently carry only a small **structured stub** of
  translated titles. **All other `insights.*` keys fall back to English** until a professional
  translation pass lands. Untranslated placeholders elsewhere are marked `[xx] English text`.

> Full professional translation of the 9 non-English catalogs is a separate content program —
> not part of the i18n foundation work.

## Adding i18n to a new surface (the pattern)

1. Add the English strings to the `en` block of `MESSAGES` in `locales.js` under a namespaced
   key (e.g. `myFeature.title`). Group related keys; reuse `insights.common.*` where it fits.
2. In the component: `import { useI18n } from '@/lib/i18n';` then `const { t } = useI18n();`
   and replace the literal with `{t('myFeature.title')}`.
3. Module-level constant arrays (labels, presets) cannot call `t`. Store a `labelKey`/`titleKey`
   on the constant and resolve it in render with `t(item.labelKey)` (see `performance-panel.jsx`
   `LAYERS`, `reports-view.jsx` `REPORT_PIVOTS`).
4. For dates/numbers, use `@/lib/format` — never `new Date(...).toLocaleDateString()` inline.
5. (Optional) add stub translations to the non-en locales, or leave them to fall back to en.

## RTL

`RTL_LOCALES` (currently `ar`) drives `<html dir="rtl">`. The three-zone shell and Tailwind
logical utilities respect direction. When adding layout, prefer logical properties / flex order
that mirror correctly rather than hard-coded left/right.
